## 2. Part 1: flicker, diagnosed with measurements
Tool: `tools/flicker_check.py` (stdlib + ffmpeg): per-frame mean temporal difference `d1` over the character region (alpha plane or luma), spikes (> 2.5x the mean of both neighbours), `rough` (jaggedness of the d1 series; smooth motion 0.01-0.2, stutter 0.45), `dups` (frames that repeat the previous one while the picture moves). `tools/frame_match.py` shows which frame of a reference each rendered frame really displays. Raw outputs: `evidence/flicker_before.txt`, `flicker_after_draft.txt`, `flicker_after_final.txt`.

**Root causes (evidence in the rows above):**
1. **Remotion `Html5Video` frame mapping (continuous flicker).** In headless render the `<video>` element does not seek frame-exactly: frames are shown late, duplicated or skipped, so the character judders/flickers although the clip itself is smooth. Seen only in stage 5/6, not in stages 1-4.
2. **NLA fallback pops (the five isolated spikes).** In `render_clip.py` a one-shot action that ends before the next event hands over to a `talk` loop; the spikes sit exactly at `event time + action length` (point_right 244+36=280, 404+36=440, 753+36=789, 885+36=921, celebrate 1204+45=1249): the arm snaps to the base pose and then blends back.
Excluded with measurements: Eevee noise (frozen pose identical), VP9 encode, specular/clearcoat popping, crown/lag bones (the sweep and the new timeline have no unexplained energy).

**Fix:** (a) the whole old action/NLA system is gone: every pose is a blend of layers, keyed on every frame, no switching (Part 2). (b) The character is composited from the **lossless RGBA PNG sequence with `<Img>`** (`Character.tsx` mode `frames`), frame n shows PNG n by construction. Cost, honestly: disk 333 MB (draft 720 px) to 742 MB (final 1080 px) per aspect clip (the old WebM was 9.6 MB); a Remotion bundle copies the work dir, so each bundle temporarily holds that too (I filled the disk once while making stills; `stills.mjs` and the preview tool now delete their bundles); render time is not worse: final render of both aspects 165 s (old: 391 s for the 16:9+9:16 final), draft 47-87 s (old 230 s).

**After** (same tool, same crops): new 16:9 `final.mp4` character region scenes 2-3: **0 spikes, rough 0.17, 0 duplicates, d1 mean 2.06** (old 17 / 0.46 / 5 / 4.17). New 9:16: 0 spikes, rough 0.18, 0 dups (old 14 spikes / 0.45 / 8). The new source clips (PNG sequences, final preset) have 1 (16:9) and 2 (9:16) "spikes" of ratio 2.5-2.7 at frames 520-522: that is the intentional scramble wiggle (4.2 Hz hands sampled at 30 fps alternate fast/slow); contact sheet `evidence/strip_frames_518-525.png` shows smooth, continuous frames. No other spike anywhere. Frozen-pose diff is 0 (stage 1).

## 3. Part 2: the performance system
Pipeline: `storyboard_v3.json` (validated before any heavy stage) -> `tts` -> `align` (adds `words.json` with word onsets/ends/sentence ends and `beats.json`) -> **`performance`** (geometry export -> solver -> Blender) -> `render` (Remotion, character as PNG frames) -> `assemble`. Runner allowlist is still id-only plus enums: `POST /run/performance/<id>?preset=draft|final&aspects=16:9|9:16|16:9,9:16` (draft default 16:9 only, final both). The old `character` stage and `timeline.json` are removed (dropped, not kept). n8n workflow `performance` (id `perf0001`, webhook `/webhook/performance`, optional body `aspects`), status flow unchanged (SCRIPTING, ASSET_GENERATION, RENDERING, AWAITING_APPROVAL). Run lock is unchanged (second request gets 409). The HTTP node timeouts were raised from 15 min to 60 min: the final performance stage (20 min) had exceeded the old limit and n8n marked run 10 FAILED while the runner kept working (I finished run 10's render and assemble by hand through the runner; the draft run 11 went through n8n end to end after the fix; **a final run through n8n itself was not repeated** for time).

**Storyboard v3 schema** (`pipeline/stages/validate.mjs`; strict: unknown keys, gestures, emotions, targets, missing cue words fail with a message; example output `evidence/validation_errors.txt`). Scene = v2 scene minus `character` plus `performance: [beat...]`. Beat: exactly one of `cue` (word; first match at or after the previous beat's cue, case/punctuation/apostrophe normalised), `at` (s from scene start), `atEnd` (<= 0, s before scene end); `gesture`, `target`, `emotion` required; `intensity` 0..1 (default 0.7), `hold` 0..4 s, `hand` L|R|auto. `target`: `viewer`, `self`, `diagram`, `node:<Name>`, `text:<i>`, `packet:<i>` (checked against the scene; `track` needs a packet).

**Geometry** (`stages/geometry.mjs` -> `work/<id>/geometry.json`, both aspects): runs `remotion/src/layout.ts`, the same pure functions the Remotion components now use (`geo`, `charPlace`, `clipRect`, `flowLayout`, `edgeSeg`, `packetXY`, `lineFont`/`typoLines`). It exports per frame the character clip rect, node centres, text line centres, packet positions every frame of their flight. Text line centres are computed analytically (flex-column arithmetic, no DOM measurement), the nodes' +-5 px bob and the text float are ignored (fine at the 60 px tolerance).

**Solver and rig** (`character/solver.py`, stdlib only; `character/render_performance.py`; `rigpose.py`; all Facet numbers in `rig_profile_facet.json`; contract `RIG_PROFILE.md`): pixel -> camera ray -> aim, solved so that the finger ray passes through the target pixel (iterated, perspective-correct), closed-form 2-link IK for hands-to-point gestures. The solver's forward kinematics agrees with the evaluated Blender rig to about 3 px (checked). Rig additions to the placeholder (my copy `lab/performance/character/`, the older labs are unchanged): brow bones, mouth split into two halves (open = scale, smile = tilt), larger floating mouth; **I also tamed the head's specular** (crystal roughness 0.18 -> 0.30, coat 0.35 -> 0.12): near-white blown facets covered the mouth. That is a change to the placeholder character look, not to layouts/backdrop/diagrams/typography.

**Layers, all always on:** speech mouth (narration amplitude, gate 0.10, closed in silence); prosody nods (content words that are long or loud, not within 0.4 s of a beat: 6 per run here); gaze (eyes saccade with 35 ms time constant, head 120 ms, head takes 85 % of the turn, back to the viewer in pauses of >= 0.25 s and at sentence ends, glances at the diagram when explaining: **0 glances happened with this dense script**, the code path exists); blinks every 2-5 s (seed 11) and after gaze shifts > 24 deg; idle breathing, torso sway, head drift (feet stay planted); crown and hand follow-through springs. Gesture timing: lead-in = the gesture's first key (0.18-0.34 s) so the apex lands on the onset; ease in/out everywhere (smoothstep tables); never two big gestures within 0.8 s: the second gets `reduceFactor` 0.5 on intensity and is composited underneath (aims still hit their target); at least one gesture per sentence (auto `beat`; 0 were needed here).

**Gestures (implemented, all in the profile):** point_at, track, present, beat, beat_repeat (3 strikes), nod, shake_head, shrug, lean_in, press, point_viewer, point_self, scramble, compare, offer, hold_palm, grip (fist), open_arms, wave. Arm modes: `aim` (straight arm hits the target pixel), `pose` (spherical angles), `ik` (hand tip at a point).
**Emotions (12, parameters in the profile):** friendly, curious, excited, playful, confident, reassuring, serious, thoughtful, satisfied, proud, emphatic, happy. Each sets eye openness, squint/arch, eye-look offset, smile, mouth width, brow raise and tilt, head roll/pitch, torso lean, idle speed, gesture amplitude. Visible in `lab/performance/sheets/emotions_faces.png` (in stills: curious = raised slanted brows and tilt, serious = brows down, happy = arched eyes and wide smile, excited = tall eyes and open mouth).
Hand choice: the hand on the side of the target; for viewer/self/centred targets alternate and avoid a hand that is still busy. Compositing: newer gesture over older, toned-down ones and the off-hand poses underneath.

## 6. Remaining flaws (honest)
- Motion was never watched in real time; judged from stills strips, consecutive-frame sheets and numbers. Audio never heard. 9:16 apex stills were looked at at reduced size only.
- Arms are two rigid links: no elbows, no fingers; pointing is a gem pointing along the arm, the hand "follow-through" is a spring and can look floppy.
- The script is dense (about 1 beat per second, 14 close pairs toned down): second gestures are weaker and the first of a pair can be cut short (the wave at the very start is cut by `press` 0.3 s later). That is a script issue worth a look.
- Gaze reaches only about 30 deg of the way to far targets; eye movement is a small shift on a flat facet (no pupils). 0 diagram glances, prosody nods only 6.
- `scramble` and `compare` use IK hand wiggles that read weakly at a distance; `offer` swings through a low arc before rising (seen in the contact sheet around frame 744).
- The wave at video start peaks 0.34 s late; text target centres are approximate (analytic, not DOM-measured).
- Timing detectors are heuristic; 7 of 31 measurable beats are off by more than 2 frames (up to 267 ms) in the measurement, not necessarily on screen.
- Some gestures happen while the character glides between layouts (scene starts); the aim uses the per-frame clip rect so it stays on target, but the glide plus gesture is busy.
- The Remotion bundle copies 1.5 GB of frames per render/still; fine now, wasteful. Disk fills quickly if bundles are left over (fixed in my tools, `render` is cleaned up by Remotion itself).
- n8n was restarted twice by me (workflow import); the older labs' runner on :8787 (pid 24139) is not mine and was left alone.
